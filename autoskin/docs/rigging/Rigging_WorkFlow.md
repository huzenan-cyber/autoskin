# 角色绑定与动画适配流程

**输入与附件识别 → 骨架确认（有附件时追加附件骨骼）→ 蒙皮（主体权重迁移＋附件自动蒙皮）→ 导出导入 → 共享骨架动画适配（含扩展骨架配套资源）＋KawaiiPhysics 附件弹性 → 替换玩家并保存。**

适用：使用 Character\_Skeleton.fbx 中的骨架和已有权重，为未蒙皮模型制作玩家角色。

角色带有尾巴、裙摆、披风、长耳、辫子或其他附件时，必须执行附件骨骼架设与自动蒙皮分支；没有附件时跳过该分支。普通贴身衣物仍按对应身体区域迁移参考权重。附件分支只在目标角色副本中追加骨骼，保留原始 Character\_Skeleton.fbx，不改变主骨架的原有骨名和父子关系。

需要柔性运动的附件默认在引擎内配置原生 `KawaiiPhysics`，实现惯性与回弹；刚性附件保持跟随，不自动添加弹性。用户明确限定附件范围、只要蒙皮或指定其他驱动时，按其要求执行。

尾巴按普通柔性附件处理：追加骨链并自动蒙皮，随身体挂接骨骼运动，由 KawaiiPhysics 提供惯性与回弹；不单独制作或播放尾巴动画，不添加尾巴专用动画层或随机调度脚本。

## 执行原则

* 每个阶段检查一次，通过后继续；后续引用结果，不重复整套验证。
* 输入、目标绑定、工具版本及相关配置未变时复用已有记录；变化后只重测受影响部分。相同资源换目录只核对内容与引用，不重新制作。
* 新角色仍需检查体型和变形。多配置对照、负例、大量帧采样和全库测试，仅在首次接入新机制、相关升级或发现异常时做。
* 已知失败要处理或明确记录；未测不算通过。完成流程中的必要检查后交付，不再追加通用验收。
* 一份制作记录即可：输入版本、骨架确认、动画关联及资源复用范围、附件弹性范围与参数、结果、已知问题、资源和回退入口。详细诊断按需保留。

## 1\. 准备输入

准备目标模型、参考 Character\_Skeleton.fbx、目标材质／贴图、现有动画和状态机。

检查文件可读、参考包含有效蒙皮、目标网格／UV／材质完整，统一单位和朝向。Blender 导入关闭自动骨骼定向；保留输入原件和未修改的参考骨架。同版本已审计过的参考和工具能力直接复用。

列出附件及其网格范围、与身体的连接位置、是否有参考权重、预期运动方式。分不清普通服装与独立附件时先说明并确认归属，不仅凭材质名判断。检查当前 UrhoX 原生导入和共享 Skeleton 对新增骨骼的支持；已有有效能力检查可复用，能力未知时先做最小兼容性检查，再批量制作附件。

柔性附件同时核对当前编辑器注册的 `KawaiiPhysics` 组件及实际属性／API，阅读 [KawaiiPhysics 使用说明](../../engine-docs/recipes/kawaii-physics.md)。能力或版本不明时先检查一条骨链；组件缺失或必需能力不支持时记录具体限制，不把仅随父骨运动标为弹性效果，也不静默换成自写求解器。

## 2\. 确认并冻结骨架

AI 先检查肩肘腕、髋膝踝、骨盆及颈头，提供正面／侧面叠加图，说明建议、调整范围及不确定项，由用户确认。未回复不算确认；同一输入、同一方案和范围已有明确确认时可沿用，新增调整重新确认。

原关节位置匹配时保留主骨架；需要调整时，只改变经确认的主关节位置及由此形成的骨长。有附件时，按第 2.3.1 节追加附件骨骼，与主骨架一起确认并冻结绑定姿势，再制作蒙皮。后续动画可以产生姿势旋转，但不能借动画适配修改已冻结的绑定骨架。

### 2.1 骨架约束

| 项目 | 标准 |
| --- | --- |
| 主骨架骨名、数量、父子层级 | 参考中的全部原有骨骼保留，建立逐骨对应；不删骨、不改名、不改变原有父子关系 |
| 原有骨骼局部坐标轴、Roll、绑定旋转 | 必须保持与参考一致，不能因移动骨端重算朝向 |
| 原有骨骼缩放 | 保持参考缩放约定，不用单根骨骼非均匀缩放改变肢长 |
| 关节位置 | 允许调整绑定姿势中的局部位移，匹配实际关节转动中心 |
| 根节点 | 保持身份、朝向、原点和 Root Motion 约定；骨盆高度可按体型调整并记录 |
| Bip001 | 调整后的绑定姿势中，位于左右大腿骨起点（髋关节中心）的三维中点；只能平移，不能旋转，保持参考绑定旋转、局部轴向及缩放 |
| 参考姿势 | 保持原 T Pose／A Pose 的姿势方向，不做 T／A 姿势转换；关节位置和骨段比例可按体型调整 |
| 主关节链比例 | 优先保留原比例，但不是硬性要求；模型有明确结构时按实际结构调整 |
| 原有辅助骨、IK 节点与挂点 | 随所属骨段调整位置，不遗留在旧体型的位置 |
| 新增附件骨骼 | 允许按已确认方案追加为原有骨骼的子分支；使用唯一名称，不插入原有父子链，不替代原有骨骼；目标骨骼总数可增加 |
| 新骨骼轴向、Roll 与缩放 | 按附件弯曲方向建立并记录；沿链保持一致的轴向和稳定的 Roll，使用单位缩放，不能以新骨轴规则改动原有骨骼 |

旋转和缩放约束针对“绑定骨架适配”，不禁止动画播放时旋转。骨骼显示箭头或显示长度不能作为实际关节位置与部件归属的唯一依据。

Bip001 的中点以左右大腿骨的关节起点计算，不取骨段中部、骨骼显示末端或大腿网格包围盒中心。在统一的模型坐标系中，满足 `P_Bip001 = (P_LThigh + P_RThigh) / 2`，并记录中点位置及允许的浮点误差。“不能旋转”指保持参考绑定旋转，不是把已有旋转清零。

改变原有骨骼的绑定旋转、局部轴向、Roll、缩放或参考姿势方向，以及增删主骨架骨骼或改变原有层级，均超出本流程的骨架调整范围。附件骨骼按第 2.3.1 节作为新增子分支处理。超出该范围时，应另行制定并确认骨架规范，不能因后续动画适配而放宽约束。

第 4 步中的 Root 包装处理仅改变独立导出副本中的对象表示方式；导出后的实际骨骼身份、数量、父子层级和有效绑定变换仍须与冻结版本对应。不能借此改变关节或轴向，也不能仅凭 Blender 骨骼数据块数量变化认定实际骨架已改变。

### 2.2 保留原骨架

1. 在绑定姿势检查骨盆、肩、肘、腕、髋、膝、踝、颈、头的位置是否适合目标模型。
2. 保持参考骨架中全部原有骨骼的名称、数量、父子关系、局部绑定位置、旋转、缩放及局部轴向不变；附件仅按第 2.3.1 节追加子分支。
3. 若复核发现实际关节中心明显不匹配，AI 助手先按本节的方案确认要求告知用户并确认调整方案，再按第 2.3 节处理；不能静默切换方案，也不能通过错误权重把网格强行拉到关节上。
4. 保存原绑定姿势快照；有附件时先完成第 2.3.1 节，再按第 2.4 节完成冻结记录。
5. 冻结记录完成，且绑定与导出回读通过后，进入第 5 步，接入共享骨架动画适配。

### 2.3 调整关节位置

以下步骤由 AI 助手执行。尚未确认的关节位置只在独立提案副本中试摆并输出叠加图；正式骨架只能应用用户已确认的调整范围。

1. **确定身体基准**：先标定脚底、骨盆中心和躯干中线，再定位胸、颈、头。依据实际转动中心，不按厚衣服或装饰外轮廓放置。
2. **定位关节链两端**：手臂先定肩和腕，腿先定髋和踝，同时检查锁骨与肩部关系。左右髋关节目标确定后，将 Bip001 只平移至两髋的三维中点，保持其参考绑定旋转、轴向及缩放。由于两根大腿骨是 Bip001 的后代，移动 Bip001 时须同步维护相关子节点的局部位移，使已确定的两髋及其他目标关节的世界位置不被父级平移意外带走；调整后重新核对中点关系。
3. **定位中间关节**：再定肘和膝。模型没有明确结构时优先沿用原上臂／前臂、大腿／小腿长度比；结构明确时以模型为准。不一律取中点，也不要求所有角色三点共线。
4. **检查链方向**：调整时保持原参考姿势展开方向，并核对肘膝弯曲平面。IK 需配置稳定弯曲方向／Pole，不能依赖完全伸直的链自行确定方向。
5. **移动关节调整骨长**：改变子关节的局部位置，不通过拉伸骨骼对象适配。工具移动 head／tail 后须重新核对局部轴、Roll 和绑定旋转，这些绑定属性不得改变。视觉位置正确还不够。
6. **同步辅助结构**：Twist 骨通常保持其在所属骨段内的相对百分比；手指、手部 IK 节点及武器挂点随手腕整体移动，脚部结构随踝调整。手脚内部比例也变化时，再逐链检查。
7. **检查对称与多视图**：对称角色采用镜像位置；正面检查宽度与长度，侧面检查前后位置，俯视检查肩髋方向。
8. **输出骨架叠加图并确认**：AI 助手显示目标网格、原骨架和拟采用骨架，标出肩肘腕、髋膝踝及关键尺寸，向用户说明变化。用户确认后，AI 助手应用并复核正式骨架，再进入冻结与权重迁移；已有确认覆盖该版本及全部调整时，引用原确认记录即可。

主关节比例与辅助骨百分比不是同一要求：主关节比例尽量接近原骨架以降低动画适配成本；辅助骨在所属段中的相对位置通常保持一致。比例变化大时，手脚落点仍可能需要 IK 或动作修正。

### 2.3.1 附件骨骼架设（有附件时执行）

在目标角色骨架副本中追加骨骼。主骨架沿用前面已确认的方案；附件架设过程中不得为迁就附件而移动、旋转、缩放或重排原有骨骼。此处新增的是同一目标骨架中的子分支，不默认拆成独立骨架。

1. **确定连接与驱动**：根据实际结构确定挂接骨骼，例如尾巴和裙摆挂骨盆，披风挂上胸，长耳挂头骨。明确刚性跟随或柔性运动范围；柔性附件默认采用第 5.1 节的原生 `KawaiiPhysics`，将模拟骨链和预期摆动一并写入骨架提案。另有专用动画／程序驱动要求时记录其控制范围与混合方式；加骨和蒙皮本身不会自动产生摆动。
2. **建立布骨路径**：尾巴、辫子等沿部件内部中心线布置，可用连续截面中心估计，再结合表面连通关系修正。弯曲或盘绕的部件保持原造型，不能把空间上接近但拓扑上远离的两段误连。裙摆、披风沿面片从固定边到自由边布置多条骨链，按前后左右或面片结构分区，不将整片衣料压成一条中心骨链。
3. **确定关节位置**：链根位于附件连接处的实际转动中心；后续关节沿中心线或面片骨链布置。先按路径弧长分段，再在弯曲明显、轮廓变化大或需要精细控制处加密，在较直、刚性区域减少关节。硬质附件可以只追加一根骨骼；骨骼数量按变形需求和引擎预算确定，不按顶点数量决定。
4. **确定长度与轴向**：相邻关节为 `P_i`、`P_(i+1)` 时，骨段长度为 `L_i = |P_(i+1) - P_i|`。尾端设在部件末端内部，最后一段的末端不必再增加独立叶骨。新骨骼的主轴沿骨段方向，使用稳定参考方向约束 Roll；弯折处检查轴向连续性，不产生突然翻转或零长度骨段。
5. **输出并确认提案**：提供正面、侧面及必要的局部叠加图，标出挂接点、骨名、父子关系、关节位置、骨段长度、数量及驱动方式。尚未确认时只修改提案副本；本次已有确认覆盖该方案和调整范围时沿用，不重复询问。
6. **正式架设并复核**：在 Blender Edit Mode 中创建 Edit Bones，设置 `head`、`tail`、`parent` 和 Roll，只追加附件子分支。原有骨骼逐骨核对不因附件架设而改变；记录新增骨骼清单和绑定变换，再与主骨架一起进入第 2.4 节冻结。

### 2.4 冻结绑定姿势与保存对应

**本节由 AI 助手通过工具逐骨比较并填写记录，向用户告知实际变更及本次适配安排。** 方案确认阶段判断“是否需要改变”，包含视觉和设计判断；本节核对“实际上是否改变”，必须依据绑定数据。用户对方案的确认不能替代数据核对。实际变化与已确认范围不一致时，先说明差异并确认处理方案，不直接冻结或进入绑定。

1. 保存原骨架和确认后的目标骨架版本，以及骨名映射、父节点、局部绑定位置／旋转／缩放、绑定矩阵及输入哈希。保留原骨架时也记录目标版本。
2. 对参考中的原有骨骼逐骨核对名称、数量、父子关系、绑定旋转、缩放、Roll 和局部轴向未变，保存新旧绑定变换及对应父骨骼坐标约定下的位置变化。保留原骨架时还须核对绑定位置未变。新增附件骨骼另记名称、父节点、关节位置、长度、轴向、Roll、缩放及绑定矩阵，核对目标总数等于原有骨骼数加新增数。共享骨架动画适配的具体配置在第 5 步执行。
3. 保存调整骨骼名单、前后位置、骨段长度及比例，以及辅助骨和挂点处理记录。调整骨架时，额外记录左右大腿骨起点、计算得到的中点、Bip001 的实际位置与中点误差，以及其绑定旋转未改变的核对结果；不满足第 2.1 节的 Bip001 约束时不得冻结。
4. **记录“骨架是否改变”**：以未修改的源骨架为基准，对照冻结后的目标骨架，填写“否（未改变）”或“是（已改变）”，并记录源／目标版本与哈希、比较的绑定数据、容差和变更骨骼清单。追加附件骨骼时整体记录为“是（新增附件骨骼）”，同时单独记录原有主骨架是否改变，不能因主骨架未变而把完整目标骨架判为未改变。结论依据实际数据，不依据前面计划选择的制作路径。
5. 目标角色的蒙皮绑定矩阵按冻结后的绑定姿势生成；调整过骨架时，不直接沿用原骨架的 inverse bind 矩阵。
6. 冻结后进入第 3 步的蒙皮制作。以后再次改动绑定骨架，必须重新核对并更新“骨架是否改变”记录，同时更新绑定数据和权重对应，并重新生成或核对依赖旧版本的动画适配数据；重新验证通过后再使用。

“未改变”要求在统一单位和坐标约定后，骨名、数量、层级、局部绑定位置／旋转／缩放及局部轴向与源骨架一致。容差只用于排除导入导出的浮点误差，不能将实际关节位置或骨长调整判为未改变。只改变网格胖瘦、服装或表面造型而未改变上述骨架数据时，可记录为未改变。

“骨架是否改变”用于追溯和确定必要复测范围。符合骨架约束时，无论骨架是否改变，均在第 5 步接入共享骨架动画适配。若发现骨名、层级、绑定旋转或缩放等超出第 2.1 节约束的变化，应先处理骨架规范问题，不能仅标记“已改变”就继续适配。无法确认时不完成冻结记录，也不进入后续制作。

权重迁移不能替代关节对齐。无论是否调整骨架，冻结后都保持已确认的骨架不变。

## 3\. 制作并清理蒙皮权重

主体及普通贴身衣物迁移参考已有权重，不对整角色使用 Automatic Weights。附件执行第 3.4 节的自动蒙皮，生成新增骨骼所需的权重；没有参考权重也必须完成该分支。两类权重最后统一清理，保持目标造型、拓扑、UV、材质和冻结骨架不变。

### 3.1 建立并检查语义分区

1. 优先利用对象、面组或已有顶点组识别部件。
2. 对合并网格，使用材质和共享边连通片辅助识别；同色部件仍需按实际用途区分。
3. 按角色结构标记头部、颈部、衣领、躯干、左右手臂、手掌、腿部及附属部件。
4. 根据真实关节链划分四肢，例如肩—肘—腕、髋—膝—踝；结合表面连通关系检查边界。
5. 检查下巴与颈部边界、肩部、背部服装、腰部配件、衣领顶面等易误分区域。不要仅凭骨骼高度把下巴切入颈部，也不要仅凭旧蒙皮标签认定不明附件的设计归属。
6. 输出分区着色图，检查正面、背面及遮挡位置，保存顶点标签和拓扑校验信息。

分区不依赖固定世界高度。角色变高或比例改变后，应依据该角色的关节位置与部件结构重新检查。

复用标签前必须核对源模型、顶点编号、面拓扑与部件含义。新角色、拓扑变化或明显造型变化需要重新建立或检查分区。蒙皮阶段读取已检查的标签。

### 3.2 配置部件与骨骼规则

以下为常见配置示例，应按角色结构和动画需求确认。骨骼名称使用实际骨架中的对应名称。

| 部件／骨骼类型 | 配置原则 |
| --- | --- |
| 头部刚性附件、帽子、面片 | 确认为附件时追加挂在头骨下的附件骨骼，刚性部件由该骨骼 100% 驱动；属于头部网格本体的面片仍按头部规则处理 |
| 颈部 | 保留胸部、颈部和头部之间的合理过渡 |
| 衣领 | 根据服装结构使用上胸、肩部等影响，排除错误头部牵动 |
| 躯干与肩部 | 保留躯干、锁骨及上臂连接处的合理过渡 |
| 上臂、前臂和腿部（含 Twist 骨骼） | 使用所属侧关节链，Twist 参与蒙皮；迁移并保留有效参考权重及合理关节过渡，将 Twist 权重纳入最终统计 |
| 手掌与手指 | 需要手指动画时保留指骨；紧凑小手可将指骨影响合入手骨，保留手腕过渡 |
| 尾巴、裙摆、披风等附件 | 按第 2.3.1 节追加附件骨骼，按第 3.4 节自动生成权重；刚性部件可用单根新增骨骼，变形部件使用骨链并处理连接过渡 |
| 根节点、控制骨、IK、挂点 | 根据节点实际用途和变形骨清单判断；不参与变形的节点保留结构，清除其网格权重 |

不能仅凭骨名决定剔除，也不能用整段单骨覆盖破坏需要保留的关节过渡。

### 3.3 建立部位对应，迁移参考权重

1. 读取参考顶点、三角面、骨骼影响和绑定矩阵，统一坐标约定及单位。保留原骨架时使用同一绑定姿势；调整骨架时分别使用原参考和冻结后的目标绑定姿势建立空间对应，不能假设两者关节位置相同。
2. 为每个目标区域配置对应参考区域、核心骨骼和允许影响骨骼。
3. 筛选该区域的候选三角面，检查端点具有合法影响，避免在部位边界插值得到无效权重。
4. 使用真实关节建立局部坐标，按参考与目标部位尺寸调整查询位置。调整骨架时沿新旧对应骨段分段映射，例如将新角色肩—肘、肘—腕上的查询位置分别映射到参考骨段，再做区域内插值；不能仅对全身统一缩放后做最近点匹配。保存匹配范围与阈值配置。
5. 仅在对应区域内查找最近表面，通过三角面的重心坐标插值已有权重。
6. 剔除该部位不允许的影响，保留剩余权重的相对比例并归一化；关节区域允许相邻骨骼共同影响。
7. 应有参考的主体区域无合法候选或有效权重时记录异常，修正对应关系后重做，不回退到全身无约束匹配。已识别为无参考权重的附件按第 3.4 节生成权重，不将主体迁移失败的区域随意改判为附件。
8. 保存源三角面、匹配距离和异常点统计，检查远距离匹配及左右串区。

对应计算只调整查询位置，不修改冻结后的骨架或目标网格。尺寸比例调整不能替代语义分区与关节对齐。

### 3.4 附件自动蒙皮

本节的自动蒙皮指按部件结构和冻结骨链程序化生成权重，无需已有参考蒙皮。主体继续使用迁移结果，附件计算只写入已确认的附件顶点及连接过渡带，不改写其他身体区域。

1. **隔离部件和影响范围**：读取已检查的附件标签，限定每个附件可使用的新增骨骼及连接处允许参与的主骨骼。相邻尾巴、左右耳、裙摆不同面片各自处理；不能按全身最近骨骼分配。
2. **骨链型部件分配**：尾巴、辫子、触须等先建立顶点到中心线的连续纵向对应，得到沿线弧长位置 `s`。盘绕部件结合网格连通性约束匹配，避免跳到邻近的另一段。在相邻骨骼影响中心的弧长位置 `c_i` 与 `c_(i+1)` 间，令 `t = clamp((s - c_i) / (c_(i+1) - c_i), 0, 1)`，可用 `h = 3t^2 - 2t^3` 平滑过渡，初始权重为 `w_i = 1 - h`、`w_(i+1) = h`。影响中心须严格递增；端部按所属骨骼延续影响。影响中心和过渡宽度按实际关节与弯曲需求配置，不机械套用统一骨长。
3. **面片型部件分配**：裙摆、披风先确定固定边、自由边及相邻骨链。沿面片纵向在同一骨链中渐变，横向在相邻骨链间平滑混合；距离和邻接以同一面片的表面关系为准，避免穿过身体、衣料夹层或裙摆开口匹配。刚性附件可直接将其顶点赋给对应新增骨骼，权重为 1。
4. **处理连接处**：尾根、耳根、裙腰或披风固定边，根据实际接合结构设置主骨骼与附件根骨之间的权重渐变。渐变范围只覆盖指定连接带；不将臀部、躯干、头部或腿部的其他顶点带入附件骨链。需要硬质连接时使用刚性跟随规则。
5. **限制自动求解范围**：如采用工具自带 Automatic Weights／热扩散等求解器，只允许作用于隔离的附件和允许影响骨骼，并将结果按顶点对应写回；核对原身体权重未被改写。不能用整角色自动权重替代主体迁移，也不能把求解失败后的空权重点随意补给最近骨骼。
6. **清理并记录**：按第 3.5 节统一处理影响数量和归一化；保存附件标签、骨链对应、影响中心、过渡范围、计算方式及异常统计。自动生成的是初始权重，仍需在第 5 步检查代表性弯曲或摆动，发现塌陷、拉伸、接缝断裂或串区时只修对应部件。

### 3.5 清理权重

1. 剔除明确不参与变形的骨骼权重。
2. 检查未知骨骼、负值和非有限值，处理异常。
3. 每顶点按权重大小保留最多 4 个骨骼影响。
4. 对剩余权重归一化，检查权重和接近 1。
5. 检查所有网格的空权重点；发现后返回对应区域定位原因，不随意补给最近骨骼。
6. 统计每点影响数、各骨骼有效影响点数及刚性部件权重，确认配置实际生效；分别统计原有骨骼与新增附件骨骼，检查附件权重没有污染其他身体区域。

上述检查在制作时完成一次，同版本已有结果按执行原则复用；异常只修复对应区域及受影响部分。常规变形观察合并到第 5 步，不再另做一套重复姿势测试。

## 4\. Blender FBX 导出与 UrhoX 导入

固定路径：**绑定工程 → 独立导出副本 → Blender 自带 FBX 导出器 → UrhoX 原生导入。**

1. 保留原绑定工程，导出副本只包含目标网格、骨架和必要挂点，保持绑定姿势。使用原装 bpy.ops.export\_scene.fbx；不改导出器、不重写 FBX，也不自行写 MDL 替代原生导入。
2. 沿用符合本次参考规范的已验证导出参数；输入坐标声明或参数变化时再校准，不能靠额外旋转／缩放掩盖错误。
3. 最终 FBX 独立回读一次，核对骨架层级／轴向／尺寸、网格、UV、材质与权重；附件存在时同时核对完整新增骨链、挂接父骨骼及附件权重，不将新增骨骼当作多余节点删除。
4. 原生导入可写目录，等待异步任务成功；核对实际加载的模型、Prefab、材质、贴图和资源引用。
5. 引擎结果回读一次：目标绑定、骨骼／挂点、LOD0 位置、UV、骨名对应权重和有效绑定矩阵正确。顶点拆分／重排需恢复对应，不能只比总顶点数。附件骨骼数量、层级、绑定和权重须与冻结版本对应；导入丢骨、合并影响或不支持扩展骨架时记录具体问题，不以删附件骨骼或改主骨架绕过。

合并保存一次导出导入检查结果。同一 FBX、相同配置已有通过结果时复用；必须项失败则修正对应阶段。引擎导入生成的 MDL 属于正常结果。

### 导出参数与 Root 特例

当前参考为厘米、Z-up；以下设置只在该约定下沿用，其他输入先核对实际单位和轴声明。

|设置|当前已验证值|
|-|-|
|选择集|仅目标 MESH、ARMATURE 和必要 EMPTY|
|Scale／Apply Unit／Apply Scalings|1／True／FBX\_SCALE\_NONE（All Local）|
|Forward／Up；主／次骨轴|正 Y／Z；Y／X|
|Space Transform／Bake Space Transform|True／False|
|Armature FBXNode Type|LIMBNODE|
|Add Leaf Bones／Only Deform Bones|False／False|
|Bake Animation／Apply Modifiers|False／False；所需修改器先在副本中处理|
|贴图|COPY、embed\_textures=True，源贴图可读|

有额外包装层时，只有 Root 是唯一顶层骨骼、所有网格均无其权重、对象空间绑定矩阵为恒等、骨架对象世界矩阵与原 Root 一致，且额外父级／附件／约束／驱动／动画依赖均已排清，才可在导出副本中由同名骨架对象承接 Root。解除子骨骼连接并保持世界变换后移除这根 Root，保持对象变换，用 LIMBNODE 导出。

处理后核对实际 Root、骨骼数量／层级和有效绑定变换。不能清除有效 Root 权重来满足前提。无权重 Root 的 inverse bind 差异须记录，并排除其他使用方依赖；不满足条件时专项处理，不机械删根。

## 5\. 接入共享骨架动画与附件弹性

本流程统一使用共享骨架动画适配，复用原动作内容及状态机逻辑。可关联原 Skeleton 时直接引用原文件；新增附件骨骼导致 Skeleton 身份不同时，按下方扩展骨架分支处理配套资源。动画适配须遵守第 2 步的骨架约束；骨架调整仍须先确认并冻结。遇到能力限制时说明具体问题并记录阻塞，不改变已冻结的绑定骨架或删除必需动画语义绕过。

* 模型与所播放动画须关联同一份共享 Skeleton，保留目标模型自身绑定姿势。能够关联原 Skeleton 时直接复用原动画、状态机及依赖。骨架完全一致时也按本节处理；已有正确关联和已验证配置时直接沿用，不为走流程额外修改骨架或增加补偿。仅骨名和层级一致不代表资源兼容。
* 优先沿用已验证公共配置：Skeleton 使用目标绑定位置；Animation 使用动画平移；AnimationScaled 按目标／源作者参考长度比例缩放动画平移。旋转继续遵循动画和混合语义。
* 按实际位移职责配置骨盆节点，不机械按骨名设置；零长度节点不直接计算比例。保留源作者姿势，不以目标绑定覆盖源参考数据。
* 用当前支持的模型关联设置，例如 import\_model 的 options.shared\_skeleton.resource，保存后核对关联和目标绑定。版本／接口改变时查实际 schema。
* 改公共策略须核对其共享角色和动画；另建公共配置时统一处理相关资源身份，不能只给角色换一份同名 Skeleton。不为每个角色烘焙整套动画，也不叠加旧差值层或对同一差异重复适配。

### 新增附件骨骼时的动画资源关联

这里的附件指追加到目标骨架中的新骨骼分支。已验证的编辑器 `0.9.0-beta.44_20261027.084213.7a4272c68b08`、官方包 `offical-3c-pubg 1.0.11` 不支持 WhiteCapTail 扩展骨架直接共用官方原动画文件：导入时骨骼数量不匹配；运行时分别拒绝不同 Skeleton 身份，以及将扩展模型直接关联原 Skeleton 的配置。见 [2026-10-28 原生兼容性验证](../../artifacts/WhiteCapTail/shared_animation_probe_20261028/README.md)。此结论限定于已测版本和机制，不是所有版本的永久限制。

1. **确定复用单位**：先检查是否已有兼容的扩展 Skeleton 和配套资源，有则直接复用。复制单位是不同的 Skeleton 身份，不是每个模型；多个角色共用同一份兼容的扩展 Skeleton 和动画逻辑时，共用一套动画、BlendSpace 和 FSM。仅骨名相同或文件同名不足以判定兼容。
2. **建立扩展资源**：没有可复用配置时，在项目可写目录通过原生导入建立包含附件骨骼的 Skeleton，保留原有骨骼的作者参考姿势、平移规则和制作来源定义，关联目标模型。保留目标自身冻结绑定，不覆盖只读官方包，不以目标绑定替换源作者姿势。
3. **复制并重新关联动画依赖**：复制实际使用的原动画及同名 XML、外部 Additive 基准等依赖，将副本统一关联扩展 Skeleton，更新副本之间的资源引用。原 `.ani` 数据保持不变，以内容哈希核对；不重新 K 身体动作，不为每个角色烘焙整库。保留 Additive、Root Motion、根锁定及制作来源语义；新资源生成独立 `.meta`／UUID，不与官方资源共用身份。
4. **接入配套动画图**：为该扩展 Skeleton 复制所需 BlendSpace 和 FSM，更新动画、BlendSpace、基准及 UUID／路径引用，避免混入仍关联原 Skeleton 的动画。保留原有身体层、参数、过渡和叠加逻辑，将配套图关联到交付场景和 Prefab。后续相同扩展骨架的角色直接共用这套配置。
5. **最小验证与版本复用**：首次接入或相关版本变化时，用独立资源对照原模型＋原动画、扩展模型＋副本动画，并检查直接复用原动画的能力。读取实际动画状态、骨骼运动和错误，不能仅凭加载成功判断可播放；Additive／AimOffset 合并到必要动作检查。同版本、同机制复用已有结果，不对每个角色重复负例或全库测试。未来引擎支持扩展兼容时，验证后改为直接引用原文件；扩展关联方案仍失败时记录阻塞。

### 附件骨骼的驱动

* 原动画继续驱动原有骨骼。原动画没有新增附件轨道时，核对附件骨骼保持目标局部绑定姿势并随父骨运动；这只构成跟随，不代表已实现独立摆动。
* 尾巴与其他柔性附件统一按第 5.1 节配置 `KawaiiPhysics`，限定物理作用的骨链范围，避免重复写入同一骨骼。没有实际驱动时不能声称尾巴、裙摆已具备动态效果；已要求的驱动无法实现时如实记录，不擅自改为刚性跟随。

### 5.1 配置 KawaiiPhysics 附件弹性

在模型原生导入、绑定回读和共享动画关联正确后执行。使用当前编辑器的原生组件配置并保存，不修改已冻结的绑定骨架、权重或原动画。完整签名及序列化字段以 [KawaiiPhysics API](../../.emmylua/KawaiiPhysics.d.lua) 为准，曲线参考 [FloatCurve API](../../.emmylua/FloatCurve.d.lua)。

1. **限定模拟骨链**：在目标 `AnimatedModel` 所在节点添加或配置 `KawaiiPhysics`，将 `Root Bone` 指向附件根骨，核对其全部后代及排除范围。不要将骨盆、头骨等主骨架误设为模拟根。相同参数的独立骨链可使用 Additional Root Bones；不同参数分开建组件，根骨范围不得重叠，也不得覆盖其他附件已有配置。刚性附件不纳入模拟。
2. **核对单位、轴向与末端**：从引擎实际导入的绑定矩阵和骨段方向确定 `Bone Forward Axis`，不能照搬 Blender 显示轴、其他角色的枚举或固定骨名。引擎使用米、Y-up；骨骼局部偏移须考虑导入缩放。末骨没有子骨且需要参与弯曲时，优先采用下表对应附件的 `Dummy Bone Length` 默认值；未列出的附件再依据冻结版本的末段长度配置。虚拟末端和骨段细分只服务于模拟，不新增导出骨骼，不改变已确认骨骼总数。
3. **设置弹性参数**：按附件长度、质量感和预期幅度选择 Component／World／BaseBone 模拟空间；使用 BaseBone 时核对基准骨存在。尾巴和马尾共用下方默认参数，短发束、长飘带和裙片采用各自的默认参数；未列出的附件按其用途调校。配置阻尼、刚度、世界位移／旋转阻尼、半径、角度限制、重力和 Alpha。配置固定子步、预热和瞬移重置阈值，避免出生、传送或突转时甩飞。`GetPhysicsSettings()` 和曲线 getter 返回副本，修改后须通过对应 setter 写回。
4. **配置必要的身体避让**：根据实际接近的骨盆、腿、胸或头部添加球体、胶囊等碰撞代理，记录驱动骨、局部偏移、朝向和尺寸；确认代理没有压住附件根部或初始造型。胶囊轴为局部 Z。裙摆／披风需要时再加跨链约束、碰撞细分或 SyncBone，不把整片衣料当作单链。代理只约束该组件的骨骼，不等于场景 `RigidBody` 碰撞或完整自碰撞，也不保证所有姿势完全无穿插。
5. **接在动画之后**：保留现有 FSM／动画播放方式，由原生组件对动画姿态追加弹性；不额外启动第二套动画播放器，也不再用脚本逐帧覆盖同一骨链。物理只影响最终蒙皮姿态，骨骼 `Node` 仍是动画姿态。需要读结果或让挂件跟随弹性时，在 `PostRenderUpdate` 中读取 `Bone:GetFinalWorldTransform()`，不跨模型切换缓存 `Bone`。
6. **验证实际效果**：先查 `GetDiagnostic()`，处理找不到根骨、范围重叠、驱动骨缺失或模型尚未加载等问题。结合下方必要动作检查观察静止、移动／转向和停下后的回弹，确认根部随挂接骨运动且不脱节、无明显甩飞或塌陷、主骨架未受模拟影响。需要数据定位时比较最终变换和动画姿态，不能只凭组件存在或 `Node` 变化判定生效。视觉检查须有实际场景或 Play 画面；预览空白不算通过。若摆动部分被提前裁剪，再检查并调整相应骨骼包围范围。
7. **保存配置与回退入口**：在第 6 步将组件、曲线、碰撞代理及相关参数保存到实际交付的场景和角色 Prefab，回读核对，而非仅留在临时预览或工具脚本中。记录模拟根、轴向、末端长度、参数和已知限制。可通过禁用组件或将 Alpha 设为 0 回到动画跟随；只有弹性参数变化时，不重新蒙皮、导出 FBX 或烘焙动画。

### 必要动作检查

从实际动作中选少量代表：待机、走跑，以及覆盖主要关节的一两个动作，如蹲下或抬臂。确认体型保持、动作确实生效、无明显错区拉伸，再看一次动作切换。

* 用到瞄准／叠加层时加测对应行为，保留基准引用；不将 additive 动作作为普通完整姿势验收。
* 有附件时，结合本次代表动作检查根部连接、骨链弯曲、KawaiiPhysics 惯性与回弹、裙摆／披风的固定边和跨链过渡，确认无明显串区、塌陷或拉伸；刚性附件检查其跟随。用户明确只要蒙皮、不接入动态驱动时，可用临时测试姿势检查蒙皮，测试后恢复绑定姿势，不把测试姿势作为交付动画。弹性检查与这些代表动作合并进行，不额外重复整套动作测试。
* 保留根锁定／根运动策略。涉及提取时走完整场景更新，不能只调用状态机 Update；涉及物理消费时，在第 6 步的简短 Play 中观察实际玩家位移。
* 新角色仍检查变形；未变化的共享机制不重复做公式推导、多配置对照、负例或固定数量的长帧测试。
* 只有实际问题、相关版本／策略变化或明确交付要求，才增加逐帧量化、极限姿势、接触 IK 或全库覆盖。

## 6\. 替换玩家并保存

本流程默认使用官方包 `offical-3c-pubg` 中的 `3CTestScene.xml` 作为玩家替换的基准场景，玩家模型节点为 `BP_PUBG/ModelNode`。除非用户另有指定，均以此场景为准，不根据当前打开的场景自动更换基准。

1. 从项目包配置和编辑器已加载的包信息确认 `offical-3c-pubg` 的实际版本、目录及只读状态，定位包内 `3CTestScene.xml`（通常为 `.cache/packages/offical-3c-pubg/<实际版本>/3CTestScene.xml`，不写死版本号）。保留该原场景作为回退入口，先另存到项目可写目录，再修改交付场景，不覆盖官方包。
2. 用编辑器原生操作替换玩家模型和完整材质列表，接入第 5 步所需动画图与引用，保留控制器、相机和场景连接。有附件时一并接入完整资源；柔性附件包含第 5.1 节的 `KawaiiPhysics` 或用户指定的驱动，保持挂接关系。
3. 保存并重新打开交付场景一次，核对实际玩家资源、附件弹性配置和重启恢复路径；交付角色 Prefab 时也须保存并回读其物理组件和动画状态机。不能只检查当前窗口显示正确，无需反复重启编辑器。制作工程、工具和诊断报告集中归档，不作为运行依赖；角色运行所需脚本、原动画及侧文件须纳入交付。
4. 简短 Play 确认实际玩家出现并播放动作，有弹性附件时确认摆动、根部连接及停下后的稳定。退出后鼠标可见且未锁定。同一资源已通过的导入／动作检查不重跑。

不要从外部重写正在打开的场景。制作资料和诊断输出集中存放，避免为零散报告反复修改项目配置、触发重启提示。
